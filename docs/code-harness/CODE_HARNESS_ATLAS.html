Plate 1

The system map

Design §1, §4, §10.1, §10.2

The harness is one JVM process. Clients and other agents send commands in. The session host gives each session one mailbox and one writer. The writer asks the pure kernel what may commit, writes the journal file, and publishes the entries to the clients. The worker runs one turn: the REPL runs the cells, and the handlers make the guest API calls through the guard and the OS sandbox. Background readers read the journal, but they never write to it.

Plate 2

The units, one inside the other

Design §3, §4.1, §6

Each unit sits inside the one above it. A session lives for good in its journal file. An activation is the part of a session that lives in one process, so the REPL definitions end with it. Turns, steps, cells and guest API calls are spans of entries in the journal.

A restart keeps the journal, the store and the preamble. It loses the definitions in the REPL, so the model gets a note that lists the lost names and the cell of each.

Plate 3

The journal tape

Design §4.1, §4.4, §4.6, choice 17

A journal is a list of facts. Read it from top to bottom: the number is the seq of each entry, and the indentation shows the turn, the step and the cell that it belongs to. Each intent is committed before its effect starts, and each outcome after the effect ends. A dot marks a commit with a full flush: each input, each activation, and the intent of a call that can change the world. Pick a case to see how a stop and a crash change the journal.

Plate 5

An approval, from start to end

Design §5.5, §8.6, choices 5 and 14

A cell never waits for a person. The call fails at once with NeedsApproval, the journal keeps the pending call, and the turn ends with a question. The person's Grant answers it in one commit, and a new turn makes the call again. The owner gets a report of each turn while the work is open.
