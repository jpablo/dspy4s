Part 1

The board, in Event Storming notation

Design §4, §5.5, §8.6, §10.3

This is the level of a workshop. Each row is one process, read from left to right. An actor or a policy gives a command, the session (the aggregate) accepts it, and one or more events become facts in the journal. A policy reacts to an event and gives the next command. Read models are what people and the LM see. The pink notes are hot spots: parts that no check has run yet.

An event can exist at several levels. Something happens outside, it becomes a command, the writer commits it as journal entries, and the entries go out to clients, to the owner and to the world:

stimulus outside→ command mailbox→ journal entry a fact→ output feeds, reports effect a call to the world signal a timer or a rule
Part 2

The flow of information in one step

Design §4.6, §5.1, §5.6, §7

One step is a loop. The context strategy reads the journal and makes the policy input. The LM writes a cell, the cell calls the guest API, and each result goes back into the journal through the writer. The next step starts from the journal again, so nothing that the journal does not hold can reach the next LM call.

What crosses each arrow

  • entries: each fact of the session, in the order of seq.
  • PolicyInput: the task, the API reference with the preamble, the status, the last observation and the history that the strategy keeps.
  • a reply: text, and maybe the code of one cell.
  • op, args: the name of the call and its arguments as Json. The intent commits before the call.
  • the result: a value as Json with its rendered text, an error, NeedsApproval or Unknown.

What never crosses

  • A secret. A handler adds it to a request, and the writer masks each known value before a commit.
  • A live REPL value. Only a Data value leaves a cell, through store, submit or rlm.
  • A call that the guard refuses. It gets an error, or NeedsApproval, and the world sees nothing.
  • A change by a derivation. Summaries and the graph read the journal, but they never write to it.
